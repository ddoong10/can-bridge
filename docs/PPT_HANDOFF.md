# can-bridge — 최종발표 정리 (PPT 제작용)

> PPT 만드는 팀원에게 넘기는 단일 요약 문서. 슬라이드로 바로 옮길 수 있게
> 항목 단위로 정리함. **평가(behavior eval) 파트는 다른 팀원 담당 → 여기 없음.**
>
> 구성: ① 중간발표 대비 바뀐 것 · ② 우리가 할 수 없는 한계 · ③ 오픈소스 연계성

---

## 0. 한 줄 정의 (표지/도입용)

> **can-bridge** = 한 AI 코딩 도구(Claude Code)의 대화 맥락을 추출·정규화해서
> 다른(또는 같은) 도구(Codex)로 이어가게 하는 CLI.
> 핵심 메시지: *"모델의 기억을 복사하는 게 아니라, 저장된 작업 기록을 가장
> 정직하게 옮긴다."*

빌드/테스트 상태(발표 시점 기준): 빌드 통과, smoke 테스트 56/56 통과.

---

## ① 중간발표 대비 바뀐 것

> 중간발표 = "도구 사이에 컨텍스트를 **옮길 수 있다**"를 보여줌.
> 최종발표 = "옮기는 걸 넘어 **얼마나 정확히 보존되는지, 무엇은 원리적으로 안
> 되는지**까지 분해하고, 실무에서 쓸 수 있게 다듬었다."

### 변화 1 — 같은 도구 왕복(round-trip)에서 **thinking/추론까지 보존**

- 예전: `Codex→Codex`, `Claude→Claude`도 중간에 **공통 형식**을 거치며
  reasoning/thinking이 **버려졌음**.
- 지금: 같은 도구로 돌아갈 땐 공통 형식을 **우회**하고 **원본 세션 라인을 그대로
  replay** → reasoning·turn_context·런타임 이벤트, 그리고 **Claude의 서명된
  thinking까지 byte 단위로 보존**.
- **라이브 검증**: 실제 `claude --resume`로 재주입된 세션을 열어 → 정상 재개 +
  이전 대화 회상 + **서명 거부 에러 없음**.
- 슬라이드 한 줄: *"다른 도구로 갈 땐 호환(공통 형식), 같은 도구로 돌아올 땐
  원본 보존(thinking 포함)."*
- 정직한 단서: 이건 *파일에 기록된* thinking 텍스트의 보존이지, 모델 내부 상태
  복제가 아님(→ ②와 연결).

### 변화 2 — 거대한 과거 transcript로 **context가 터지는 문제** 대응 (옵션)

긴 세션을 통째로 넘기면 받는 쪽 context가 과부하됨. 그래서 **opt-in 옵션**으로
용량을 조절(기본은 fidelity 우선, 건드리지 않으면 기존과 동일):

| 옵션 | 하는 일 | 상태 |
|---|---|---|
| **compacted 라인 인식** | 소스 세션의 최신 압축(compaction) 지점을 인식, 그 이후만 살림 | ✅ 구현 |
| **`--since-compact`** | 전체가 아니라 **마지막 compact 이후의 실질 작업만** `.cbctx`로 | ✅ 구현 |
| **`--max-tool-output-chars n`** | 긴 tool_result/출력은 **n자에서 잘라** 저장(절단 표시 남김) | ✅ 구현 (예: 20000자→500자) |
| **`--context-mode full \| slim`** | `full`=최대 보존(기본), `slim`=이식/공유용(자동으로 since-compact + 출력 절단 + native 제외) | ✅ 구현 |
| **`--no-native`** | 같은 도구 백업용 원본(native) 동봉을 끔(용량↓) | ✅ 구현 |
| **`.cbctx` budget 메타데이터** | 패키지 안에 *무엇을 몇 개/몇 자 버렸는지* 기록(droppedMessages, truncatedToolOutputs, omittedChars) → 어디서 터지는지 확인 가능 | ✅ 구현 |
| `.cbctx inspect` 전용 명령 | 패키지 안에서 어떤 tool output이 context를 키우는지 보여주는 별도 명령 | 🔜 후속(미구현, 위 메타데이터로 부분 대체) |

- 슬라이드 한 줄: *"긴 대화를 통째로 넣지 않고, 압축 이후 + 큰 출력 절단으로
  '이식용 경량 패키지(slim)'를 만들 수 있다 — 단, 기본은 최대 보존."*

### 변화 3 — 그 외 충실도·이식성 개선 (단순 변환기 → context 패키지)

- **양방향 + 도구 호출 구조 보존**: `tool_use/tool_result ↔
  function_call/function_call_output`. 추가로 **짝 없는 호출 메움 / 대화 순서
  보존 / 빈 식별자 제거**.
- **Foreign tool 오인 방지**: Claude의 `Read`/`Bash` 같은 도구 이력을 Codex에
  넣을 때 `foreign_tool:claude-code:Read`로 표시 + "이건 과거 다른 도구의
  기록이고 지금 호출 가능한 도구가 아니다"를 안내 → 타겟이 자기 도구로 오인 방지.
- **repo 상태 검증**: 추출 시 git(branch·commit·dirty) 스냅샷 → 받는 쪽
  workspace와 다르면 **경고**(과거 파일 상태를 현재로 착각 방지).
- **`.cbctx` 공유 패키지**: 같은 머신뿐 아니라 **다른 사람/환경에 파일 하나로
  전달**. 안에 normalized 대화 + (옵션)repo 메타/patch + redaction 정보 +
  doctor 결과 + 무결성 해시 + (옵션)native 원본.
- 슬라이드 한 줄: *"단순 변환기에서, 검증·공유·복원이 되는 context 패키지로."*

## ② 우리가 할 수 없는 한계 (정직하게)

> 모든 한계의 뿌리: 이건 **session migration(세션/에이전트 복제)이 아니라
> context import(작업 기록 이식)**. "파일에 글로 남은 건 옮긴다. 모델 머릿속·
> 숨은 설정은 못 옮긴다."

세 등급으로 나눠서 말하면 깔끔함:

### A. 고친 것 (코드+테스트로 닫음)
- 짝 없는 도구 호출 / 대화 순서 / 빈 식별자
- 도구 이름 오인(마킹) · 작업 폴더 불일치(경고)
- 같은 도구 round-trip 손실(native 보존)

### B. 완화는 되나 손실 0은 불가능
- **도구 의미 매핑** — 이름은 표시해도 `Bash↔shell_command`처럼 기능을 1:1로
  바꾸진 않음(의도적 범위 밖). `TodoWrite/Task/MCP`는 대응 도구 자체가 없음.
- **추출 시 노이즈성 라인 손실** — 세션 파일의 상당 부분이 hook/UI 메타라
  버림(대부분 의도된 것). 일부 실입력은 선별 복구 여지.
- **숨은 컨텍스트** — 시스템 프롬프트·`CLAUDE.md`/`AGENTS.md`·MCP 도구 목록은
  세션 파일에 본문이 없어 미전이.
- **긴 컨텍스트** — 옵션으로 줄일 수 있지만, 요약은 본질적으로 손실.

### C. 원리적으로 불가능 (받아들이고 "경계"로 선언) ← 발표 강조 포인트
- **모델 내부 실행 상태 = KV cache · attention state · 내부 reasoning state.**
  세션 파일 **밖**(모델·런타임 안)에만 존재 → 외부 도구가 추출/복제 불가.
- **벤더 숨은 시스템 프롬프트** — 파일에 없음.
- **이미 압축(compaction)된 원본 대화** — 업스트림에서 이미 소실.
- **다른 모델이 같은 기록에서 똑같이 행동한다는 보장** — 모델이 다르면 같은
  맥락도 다르게 행동.

> 발표 멘트: *"`/resume`조차 모델의 기억을 되살리는 게 아니라 저장된 기록을 다시
> 읽는 것입니다. KV cache나 내부 상태는 파일에 없어서 누구도 못 꺼냅니다. 그래서
> 우리의 목표는 agent 복제가 아니라, 관찰 가능한 작업 기록의 충실한 이전입니다.
> 이건 실패가 아니라 제품의 경계입니다."*

## ③ 오픈소스 연계성

### (a) "오픈"이라서 가능했다 — 로컬 파일 기반
- Claude Code·Codex는 대화를 **사용자 로컬 파일**(`~/.claude`, `~/.codex`)에 남김.
  서버에 갇힌 게 아니라 디스크에 있어서 외부 도구가 읽고 변환 가능.
- 단, 그 포맷은 **공개 안정 API로 문서화돼 있지 않음** → 우리가 실제 파일을
  reverse-engineer. (웹/앱 컨텍스트는 서버측이라 우리 도구로 못 뺌 = 로컬 CLI를
  택한 이유.)

### (b) 선행 오픈소스와의 관계 — "최초"가 아니라 "차별점"
- 이미 비슷한 브릿지/MCP 프로젝트가 여럿 있음(예: `ai-session-bridge` =
  Claude↔Codex JSONL 변환, 그 외 라이브 브릿지·MCP 래퍼류).
- can-bridge의 차별점:
  - **양방향 end-to-end 검증** (선행 일부는 한 방향 미검증)
  - **손실을 인지(loss-aware)** — 무엇이 얼마나 손실되는지 문서화
  - **같은 도구는 원본 보존(native)** + **다른 도구는 공통 형식** 2층 설계
  - 런타임 의존성 **0** → 작고 가벼운 코어

### (c) 다른 오픈소스 위에/아래에 얹히는 위치
- can-bridge는 **라이브 에이전트 라우터가 아니라 context 교환 계층(interchange
  layer)**.
- 여러 에이전트를 운영하는 orchestration 프레임워크(예: OpenClaw/Hermes류)가
  있다면, can-bridge는 그 에이전트들이 **주고받을 context artifact를 표준화하는
  하위 계층**으로 MCP/어댑터로 붙을 수 있음.

### (d) 자체도 오픈소스 + 재현 가능한 협업 패턴
- 레포 공개(npm `can-bridge` / GitHub 설치).
- 개발 자체를 **Claude Code와 Codex가 레포 문서로 인계·교차 리뷰**하며 진행 —
  우리가 푸는 문제(컨텍스트 공유)를 **개발 방식으로 시연**한 셈.

> 발표 멘트: *"이미 다리는 많습니다. 우리의 기여는 최초의 다리가 아니라, 무엇이
> 손실되는지 아는 교환 코어 + 같은 도구로 돌아갈 땐 원본을 보존하는 2층 설계입니다."*

## 부록 — 슬라이드 추천 순서 (참고용)

1. 표지 / 한 줄 정의
2. 문제: 맥락이 도구 안에 갇힘
3. 핵심 아이디어: resume = 저장된 기록 다시 읽기
4. 구조: 꺼내기 → 공통형식 → 넣기 (+ same-tool 원본 보존 곁가지)
5. **[변화 1]** round-trip thinking 보존 (라이브 검증)
6. **[변화 2]** 긴 대화 context 폭발 대응 옵션
7. **[변화 3]** 충실도·이식성 개선 + `.cbctx` 공유
8. **[한계]** A/B/C — 특히 C(KV cache·내부 상태)
9. **[오픈소스]** loss-aware 교환 코어 + 선행 대비 차별점
10. 마무리: "기억을 복사하지 않는다, 회의록을 가장 정직하게 옮긴다."
